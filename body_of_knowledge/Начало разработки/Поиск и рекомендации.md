## Что и зачем
Есть много страниц, на которых хочется показывать список различных "документов": товаров, публикаций, мастеров. В сценариях, на которых от пользователя поступает текстовый запрос, список будет формироваться на основе текстовой релевантности (поиск); в сценариях, где текстового запроса нет - на основе предпочтений пользователя (рекомендаций)
## Кандген и финализация
Нужно уметь унифицированно строить такие страницы в разных сценариях.
Делать это имеет смысл в 2 этапа: кандидатогенерация (кандген) + финализация. На обоих этих этапах происходит фильтрация и ранжирование документов. Отличие этих шагов в используемых подходах и технологиях: кандген можно делать с помощью готовых поисковых и рекомендательных движков, при этом выбор кандгена зависит от сценария. Финализация же осуществляет фильтрацию и ранжирование на основе тех данных, которые сложно доставить в GIN поиского движка или фидбэк рекомендательного, и подходы к финализации в целом схожи на разных сценариях.

Типичный сценарий: пользователь открывает страницу/вводит параметры. На основе сценария выбирается кандген движок - поисковый или рекомендательный. На вход кадгену поступает текстовый запрос/id пользователя, фильтры. Кандген движок возвращает большую страницу кандидатов (например, 200 товаров или 50 публикаций), соответствующих переданным фильтрам и, возможно, отранжированным по специфичным для кандгена правилам (для поиска - текстовой релевантности, для рекома - скор от модели). Финализатор затем применяет общие правила фильтрации (например, товар должен быть в продаже. В идеале, это признак и другие признаки можно было бы использовать в кандгене, но данные до кандгена довозятся eventually, так что фильтровать нужно и на финализации тоже), доп. правила ранжирования (например, штраф товарам мастера с высоким уровнем отмен) или вообще отранжировать с нуля (например, если пользователь попросил публикации по-новее или товары по-дешевле; в этом случае кандген стоит настроить так, чтобы на ранжирование тратилось как можно меньше времени). Наконец, после ранжирования, финализатор выбирает малую страницу и отправляет на клиент (пагинация обычно производится по 8/16 документов, чтобы не утыкаться в плохую сеть или слабые клиентские устройства).

> А зачем тогда запрашивать так много кандидатов - не легче ли на страницу из 8 товаров запросить с небольшим запасом, например, 16?

Это значительно ухудшит качество выдачи. Пример: на странице с поисковым кандгеном пользователь попросил отранжировать по цене. Если кандген не умеет ранжировать по цене (не уверен, мб такое простое ранжирование и поддерживает), то товары из разных страниц кандидатов невозможно правильно упорядочить (потому что ранжирование происходит в рамках одной страницы кандидатов). Чем меньше страницы кандидатов, тем более заметны недочеты двухэтапной системы.
## Как будем реализовывать
### Движки кандгена
Для рекомендаций - open source движок gorse - https://gorse.io/
Для поиска - open source движок - https://www.meilisearch.com/ (страничка рекламирует облако и SaaS, но на самом деле есть open source self-hosted версия)
### Финализация
Пишем свой микросервис
### Какие фильтры и кастомные сортировки поддерживаем
Для товаров - фильтр по категории (пользователь может указать), фильтр по мастеру (нужно для страницы мастера), ранжирование по цене (пользователь может указать)
Для публикаций - фильтр по мастеру (нужно для страницы мастера), ранжирование по новизне (пользователь может указать)
Для мастеров - ранжирование по алфавиту, по подпискам
